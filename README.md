# 골라!

> **규칙** 위에서 떨어지는 도형 중 지금 조건에 맞는 색만 탭한다. 아닌 것은 그냥 보낸다.
> **스킬** 억제(누르지 말 것을 참기) + 반응.

브라우저에서 바로 돌아간다. `index.html` 하나가 전부다. 빌드도, 외부 라이브러리도, 에셋도 없다.

```bash
npx http-server -p 8080 -c-1 .   # 또는 index.html 을 그냥 연다
npm test                          # 자동 플레이 봇 + 재현성 검증
```

---

## 1. 규칙

- 레인 하나. 도형은 상단(-40px)에서 생성되어 바닥(y=600)으로 떨어진다.
- 화면에 여러 개가 있어도 **활성 도형은 가장 아래 하나**뿐이다. 밝게 빛나는 그것에 탭이 적용된다.
- HUD 중앙의 **현재 조건**(색 원 + 이름)과 활성 도형의 색이 같으면 탭, 다르면 참는다.

| 상황 | 결과 |
|---|---|
| 탭 · 색이 조건과 같음 | **HIT** `+10 × 구역 배율` |
| 탭 · 색이 조건과 다름 | **WRONG** 목숨 −1, 250ms 정지 |
| 안 탭 · 조건 도형이 바닥 도달 | **MISS** 목숨 −1 |
| 안 탭 · 비조건 도형이 바닥 도달 | **PASS** ±0 |
| 활성 도형이 없을 때 탭 | 무시. 벌점 없음(HUD 조건이 살짝 흔들린다) |

목숨 3개. 0이 되면 게임 오버.

색은 4종이고 **색맹 보조 기호**가 함께 들어간다 — 파랑 ●, 빨강 ▲, 노랑 ■, 초록 ◆.
조건 HUD·배너·타이틀 모두 같은 기호를 쓴다.

## 2. 점수식

```
HIT 점수 = 10 × 구역 배율
구역 배율 = 탭 순간 도형 중심의 y 로 결정
            y <  200  →  ×3
            y <  400  →  ×2
            그 외      →  ×1
```

콤보 없음. 연속 보너스 없음. 아이템·스테이지·업그레이드 없음. **위험-보상 축 하나뿐이다**(원칙 8).

### 높이는 고르는 게 아니라 벌어들이는 것 — 이 게임의 핵심

요청서를 그대로 구현하면 이런 성질이 저절로 나온다. 설계 의도보다 좋아서 그대로 뒀다.

활성 도형은 항상 **가장 아래 하나**다. 그래서 탭 높이를 마음대로 고를 수 없다.

- 비조건 도형이 앞을 막으면 그게 **바닥까지 떨어질 때까지 기다려야** 한다.
  그동안 뒤의 도형들이 쌓인다. 막던 도형이 사라지면 다음 도형은 `600 − (speed×gap)` 위치에서
  활성화된다 — 즉 **낮은 곳**.
- 거기서부터 조건 도형을 연달아 빠르게 처리하면 활성 위치가 한 번에 `speed×gap` 씩 **올라간다**.
  ×2 → ×3 → 계속 ×3.
- 그런데 빠르게 치는 리듬에 들어간 순간, 다음이 비조건 도형이면 그대로 눌러버린다(억제 실패).

**빨리 칠수록 높이 올라가고, 높이 올라가려면 생각할 시간을 포기해야 한다.**
탐욕이 곧 리듬이고, 리듬이 곧 오답 위험이다. 봇 수치로도 확인된다(4장).

## 3. 난이도 — `DIFFS` 표 하나

레벨은 **처리된 도형 수**로 오른다. 튜닝은 이 표만 고친다.

```js
const DIFFS = [
  { upTo:  15, speed: 3.4, gap: 64, lure: 0.38, switchEvery: 12 },
  { upTo:  35, speed: 4.0, gap: 55, lure: 0.44, switchEvery: 10 },
  { upTo:  60, speed: 4.6, gap: 48, lure: 0.48, switchEvery:  9 },
  { upTo:  90, speed: 5.3, gap: 42, lure: 0.52, switchEvery:  8 },
  { upTo: 130, speed: 6.0, gap: 37, lure: 0.55, switchEvery:  7 },
  { upTo: Infinity, speed: 6.8, gap: 33, lure: 0.55, switchEvery: 6 },
];
```

| 레벨 | 도형 간 거리 `speed×gap` | 상단 구역(200px) 통과 | 도형/초 |
|---|---|---|---|
| 0 | 218px | 0.98초 | 0.94 |
| 1 | 220px | 0.83초 | 1.09 |
| 2 | 221px | 0.72초 | 1.25 |
| 3 | 223px | 0.63초 | 1.43 |
| 4 | 222px | 0.56초 | 1.62 |
| 5 | 224px | 0.49초 | 1.82 |

### 왜 요청서 초안 값을 고쳤나 (요청서 4장이 허용한 튜닝)

초안은 `speed×gap` 이 165~189px 이었다. 이 값이 **200px 미만이면 ×3 이 사실상 사라진다**:

> 비조건 도형이 바닥(600)에서 사라진 직후 다음 도형의 y 는 `600 − speed×gap`.
> 초안 값으로는 `600 − 165 = 435` — 언제나 **×1 구역**. 거기서 한 번 올라가야 겨우 ×2 다.
> 비조건 비율이 40~60%라 연속 조건 도형이 3개 이상 이어지는 일이 드물고, 결국 대부분 ×1·×2 로 끝난다.

측정하면 `perfect` 봇 평균 배율이 ×1.96, **safe/perfect = 51%** 로 완료 기준 4(40% 이하)를 못 넘는다.

그래서 `speed × gap` 이 **항상 200px 을 넘도록** 표 전체를 다시 맞췄다.
그러면 위 상황에서 다음 도형이 `600 − 220 = 380` → **×2 구역**에서 활성화되고,
거기서부터 연속 처리로 ×3 까지 올라간다. 결과: 평균 배율 ×2.6, **safe/perfect = 37.5%**.

`lure` 도 초안(0.40~0.60)에서 조금 낮췄다(0.38~0.55). 고레벨에서는 속도만으로 이미 충분히 어렵고,
비조건 비율이 높을수록 "막힌 채 기다리는" 시간이 늘어 ×3 이 다시 멀어진다.
속도는 초안보다 조금 올려(3.0→3.4 … 6.3→6.8) 도형/초는 초안과 비슷하게 유지했다.

## 4. 봇 결과

`node test/autoplay.mjs --seeds 12 --max 120` (상한 120초)

| 봇 | 생존(초) 평균 | [최소~최대] | 점수 평균 | 점수/초 | 평균 배율 | ×3 / ×2 / ×1 |
|---|---|---|---|---|---|---|
| perfect     | 120.0 (안 죽음) | [120~120] | 1,565 | 13.0 | ×2.58 | 429 / 293 / 5 |
| react(200)  | 65.7 | [11.7~118.5] | 655 | 10.0 | ×2.07 | 166 / 75 / 138 |
| **react(300)** | **66.6** | [16.3~119.8] | 653 | 9.8 | ×2.06 | 161 / 82 / 137 |
| react(400)  | 67.1 | [16.3~120.0] | 607 | 9.0 | ×1.91 | 119 / 110 / 151 |
| safe        | 120.0 (안 죽음) | [120~120] | 588 | 4.9 | ×1.00 | 0 / 0 / 705 |

**완료 기준 4 전부 통과** — perfect ≥ 90초 / react(300) 45~75초 / safe ≤ perfect의 40%(37.5%).
`replay()` 점수 일치도 35판 전부 통과(완료 기준 3).

> **이 수치는 밸런스 확인용이고 재미의 증거가 아니다.** 재미는 직접 10판 해보고 판단한다.
> (프로젝트 지침)

### 수치가 말해주는 것 — 두 축이 깨끗하게 분리된다

`react(ms)` 봇은 5% 확률로 색을 오판한다. 반응 지연만 바꿔가며 24시드로 재보면:

| 반응 | 점수/초 | 평균 배율 | 생존(초) |
|---|---|---|---|
| 0ms (perfect) | 13.0 | ×2.57 | 안 죽음 |
| 150ms | 9.9 | ×2.06 | 63.4 |
| 300ms | 9.7 | ×2.05 | 64.4 |
| 450ms | 8.1 | ×1.74 | 65.2 |
| 600ms | 6.5 | ×1.41 | 59.5 |
| safe(무한대) | 4.9 | ×1.00 | 안 죽음 |

- **점수는 반응 속도가 정한다.** 0ms → 무한대 사이에서 점수/초가 13.0 → 4.9, **2.7배** 차이.
  위험-보상 축이 실제로 작동한다.
- **생존은 반응 속도와 거의 무관하다.** 450ms 까지는 생존이 안 바뀐다.
  오판(5%)만 죽인다. 반응이 500ms 를 넘어야 비로소 MISS 가 생긴다
  (오판 0%인 react(600) 봇도 24판에 21번 놓쳤다).

즉 **반응 = 점수, 억제/판단 = 생존.** 두 축이 서로 간섭하지 않는다.
이게 좋은 설계인지 나쁜 설계인지는 사람이 10판 해봐야 안다(5장).

### 걸리는 점

`react(300)` 생존 편차가 16.3초 ~ 119.8초로 매우 크다. 목숨 3개 + 독립적인 5% 오판이면
기하분포라 당연한 결과지만, 사람에게는 "이번 판은 왜 15초 만에 끝났는지 모르겠다"로 느껴질 수 있다.
다만 봇의 5%는 상황과 무관한 고정값이고, 사람의 오판율은 레벨·속도·리듬에 따라 움직인다.
**플레이테스트에서 짧은 판이 실제로 억울하게 느껴지는지 확인할 것.**

## 5. 재현성 (원칙 1)

- 게임 로직의 난수는 `mulberry32(seed)` 하나뿐이다. 연출(파편·흔들림)에만 `Math.random` 을 쓴다.
- 시드가 정하는 것: 도형 색 순열, 조건 색, 조건 전환 시점(±1 지터). **결과는 정하지 않는다.**
- **고정 타임스텝**이라 주사율과 무관하게 같은 틱 열을 밟는다. 입력 로그 `[{t: ms}]` 의 `t` 는
  틱 번호와 1:1 대응한다.
- 게임 오버 화면의 `시드 · 재현` 버튼 → `window.__judge.replay(seed, inputs)` 로 다시 돌려
  점수가 같은지 화면·콘솔에 표시하고, 이어서 그 판을 그대로 재생한다.

## 6. 저장 · 리더보드

- 로컬 최고 기록: 어댑터(`window.storage` → `localStorage` → 메모리)에 키 `judge:best`,
  값 `{score, seed, inputs}`.
- 온라인 리더보드는 Supabase REST 를 `fetch` 로 직접 호출한다. **지금은 꺼져 있다** —
  이 저장소에 붙은 Supabase 프로젝트가 아직 없어서 URL/키가 비어 있다. 켜려면 둘 중 하나:

  ```js
  // index.html 안의 const LB = Object.assign({ url:'', key:'', table:'judge_scores' }, ...)
  // 또는 index.html 보다 먼저 실행되는 스크립트에서
  window.__judgeLB = { url: 'https://xxxx.supabase.co', key: '<anon key>' };
  ```

  테이블: `judge_scores(name text, score int, seed text, created_at timestamptz default now())`.
  RLS 는 `select` 전체 허용 + `insert` 전체 허용으로 둔다.
  URL 이 비어 있으면 네트워크 호출을 아예 하지 않고, 켠 뒤 실패해도 게임은 그대로 돈다.
- 1위 점수를 받아오면 HUD 왼쪽 아래에 `세계 1위 23,000` 으로 **플레이 중** 표시한다(원칙 6).

## 7. 프로젝트 지침을 어긴 곳과 이유

| 어긴 것 | 어떻게 | 왜 |
|---|---|---|
| 요청서 4장 `DIFFS` 초안 값 | `speed`·`gap`·`lure` 전부 재조정 | 초안으로는 ×3 이 사실상 도달 불가능하고 완료 기준 4를 못 넘는다. 3장 참고. 요청서 4장이 허용한 튜닝 |
| 요청서 2.4 전환 시퀀스 | "1.2초 공백 **→** 배너 0.8초 **→** 조건 변경"을 순차(2.0초)가 아니라 **봉투(총 1.2초)** 로 읽었다. 배너는 공백 시작과 동시에 뜨고, 0.8초에 조건이 바뀌고, 1.2초에 생성 재개 | 순차로 읽으면 한 판에 10~15회 × 2.0초 = 20~30초가 죽은 시간이 된다. 원칙 5(짧은 코어 루프)와 정면으로 부딪힌다. "1.2초 동안 생성 없음"·배너 0.8초·순서는 모두 지켰다 |
| 요청서 2.1 HUD | HUD 바(y 0~52)가 ×3 구역 위쪽을 덮는다 | 구역 경계(0/200/400/600)는 요청서 그대로 두고, 대신 도형은 **y ≥ 78** 이 되어야 활성화된다. 탭할 수 있는 도형이 가려지는 순간은 없다. 그 위의 도형은 반투명 HUD 뒤로 비쳐 보인다 |
| 요청서 3.2 WRONG 문구 위치 | `✕ 이건 빨강` 을 도형 "옆"이 아니라 위/아래에 | 22px 문구가 ~140px, 레인 폭이 244px. 1.6배로 커진 도형 옆에는 안 들어간다 |
| 요청서 2.5 게임 오버 배경 | 마지막 실패 도형을 죽은 위치가 아니라 고정 위치(y=386)에 붉게 | 죽은 위치에 그리면 점수·통계 텍스트와 겹친다. 도형 아래에 `마지막: 초록을 눌렀다` 를 붙여 "왜 죽었는지"를 한 줄로 남긴다 |
| — (요청서에 없음) | 마지막 목숨을 **MISS** 로 잃으면 380ms 멈춘다 | WRONG 만 정지가 있으면, 놓쳐서 죽었을 때 원인을 못 보고 화면이 넘어간다. 원칙 4 |
| 요청서 7장 `state()` | `active` 에 `id`·`mult`, 최상위에 `timeMs`·`tick`·`processed`·`stats`·`phase`·`seed`·`frozen` 추가 | 봇이 "같은 도형"을 추적하고 생존 시간을 재려면 필요하다. 요청서 필드는 그대로 다 있다 |
| 요청서 9장 산출물 | `package.json`·`.gitignore`·`docs/` 추가 | `package.json` 은 Playwright 를 `npm test` 로 돌리기 위한 것(게임 자체는 여전히 의존성 0). `docs/` 에는 상위 지침과 이 게임의 개발 요청서 원본을 넣어 저장소만으로 판단 근거가 닫히게 했다 |
| 요청서 6장 리더보드 | 구현했지만 꺼져 있다 | 이 저장소에 붙은 Supabase 프로젝트가 없다. 6장에 켜는 법을 적었다 |

## 8. 하지 않은 것 (원칙 9)

콤보, 연속 보너스, 아이템, 스테이지, 캐릭터, 업그레이드, 모양 조건, 복합 조건, 부정 조건 —
전부 없다. 코어 루프가 재미있다고 확인되기 전에는 붙이지 않는다.

### 다음에 시험해 볼 것 (코드 말고 여기에만 적는다)

1. **높이를 직접 고르게 할 것인가.** 지금은 높이를 "벌어들인다". 대신 활성 도형을
   가장 아래 하나가 아니라 화면의 아무 도형이나 되게 하면 매 도형마다 위험을 고를 수 있다.
   단 그러면 입력이 "탭"에서 "조준"이 되어 원칙 3을 깬다. 2nd-game 의 실패와 같은 방향이다.
2. **반응 축을 생존에도 걸 것인가.** 지금 500ms 아래에서는 반응이 생존에 영향이 없다.
   `speed × gap` 을 200px 근처까지 낮추면 반응이 생존을 정하게 되지만,
   그 순간 ×3 이 사라진다(3장). **둘은 같은 노브의 양 끝**이라 동시에 만족시킬 수 없다.
   이게 이 게임에서 나온 가장 중요한 구조적 발견이다.
3. **목숨 3개가 맞는가.** 생존 편차가 크다(4장). 5개로 늘리면 편차는 줄지만 한 판이 길어진다.
