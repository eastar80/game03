> **스킬** 억제(누르지 말 것을 참기) + 반응.

브라우저에서 바로 돌아간다. `index.html` 하나가 전부다. 빌드도, 외부 라이브러리도, 에셋도 없다.

## 1. 규칙

- 레인 하나. **화면에는 언제나 도형이 하나뿐이다.** 늘 맨 위 HUD 뒤에서 나와 바닥으로 떨어진다.
- HUD 중앙의 **기준**(색 원 + 이름)과 같은 색이면 탭, 다르면 참는다.
- **기준은 매 도형마다 바뀐다.** 전환을 알리는 정지도 배너도 없다 —
  HUD 가 `[지금] 노랑 › [다음]` 을 **상시로** 보여주기 때문이다.
  기준은 큐처럼 한 칸씩 밀린다: 도형이 끝나면 「다음」이 「지금」자리로 미끄러져 온다.
- **오른쪽 여백에 점수 기록이 쌓인다.** 방금 얻은 점수가 맨 위에 얹히고
  과거는 한 칸씩 아래로 밀리며 옅어진다. 레인 밖이라 판정 화면과 겹치지 않는다.
- **도형은 고정된 박자로 온다.** 약 0.95초마다 하나씩, 플레이와 무관하게.
  빨리 끊으면 그만큼 레인이 비고, 그 틈이 **다음 기준을 읽는 시간**이 된다.
  바닥선 아래의 얇은 막대가 다음 도형까지의 박자를 보여준다.

| 상황 | 결과 |
|---|---|
| 탭 · 색이 조건과 같음 | **HIT** `+10 × 구역 배율` |
| 탭 · 색이 조건과 다름 | **WRONG** 목숨 −1, 250ms 정지 |
| 안 탭 · 조건 도형이 바닥 도달 | **MISS** 목숨 −1 |
| 안 탭 · 비조건 도형이 바닥 도달 | **PASS** ±0 |

목숨 3개. 0이 되면 게임 오버.
색 4종에는 **색맹 보조 기호**가 함께 들어간다 — 파랑 ●, 빨강 ▲, 노랑 ■, 초록 ◆.

## 2. 점수식 — 그리고 이 게임의 유일한 축

```
HIT 점수 = round( 30 × (1 − p)^1.4 ),  최소 1점
p = 판정 구간(52~600) 안의 진행도.  0 = 맨 위(막 나타남), 1 = 바닥

맨 위 30점 ─── 22 ─── 15 ─── 8 ─── 바닥 1점
```

**칸이 아니라 연속이다.** 1ms 가 전부 점수에 반영된다.
레인 **왼쪽**의 네 눈금(30 / 22 / 15 / 8)이 점수 사다리이고 **오른쪽**은 방금 얻은 점수의 기록이다.
색·크기·소리는 그대로 띠에서 가져온다 — 숫자는 정밀하게, 느낌은 또렷하게.

콤보 없음. 아이템 없음. 스테이지 없음. **위험-보상 축 하나뿐이다**(원칙 8).

곡선이 완전한 직선이 아니라 지수 1.4 로 살짝 휘어 있는 데는 두 가지 이유가 있다:
아래쪽 40% 가 거의 평평해서 **"이미 늦었으면 쉬어가는" 구간**이 남고(직선은 끝까지
1ms 를 다투게 해서 피로하다), 직선이면 safe/perfect 점수비가 40% 라 완료 기준 4에 걸린다.
`?score=linear`(순수 직선) / `?score=tier`(옛 ×1~×4)로 되돌려 비교할 수 있다.

### y 는 위치가 아니라 시간이다

도형은 언제나 하나이고 언제나 맨 위에서 시작한다. 그래서 **탭한 높이 = 네가 망설인 시간**이다.
구역 경계는 픽셀이 아니라 시간으로 잡았다(활성화된 순간 기준):

| 눈금 | 레벨 0 | 레벨 5 | 뜻 |
|---|---|---|---|
| 30점 | 0ms | 0ms | 알기 전에 지른다 (도박) |
| 22점 | 153ms | 131ms | |
| **15점** | **~306ms** | **~262ms** | **아는 순간 바로 친다 — 인식 시간 경계** |
| 8점 | ~458ms | ~393ms | 알고 나서 친다 (안전) |
| 1점 | ~761ms | ~652ms | 망설였다 |
| 그 뒤 | 바닥 = **MISS** | 바닥 = **MISS** | |

눈금 사이는 전부 연속이다. 306ms 에서 1ms 빨라지면 그만큼 점수가 오른다.

### 15점 눈금은 인식 시간에 붙잡아 둔다 — 이 게임에서 가장 섬세한 숫자

기획자의 3차 플레이테스트 보고가 이 설계의 핵심을 짚었다:

> "나의 감각으로는 ×3의 거의 끝에서 인식하게 돼. 그래서 틀려도 칠지, 안전하게 내려올지 고민하게 돼."

사람의 색 판단은 대략 300ms 다. **그 선이 어느 칸에 떨어지느냐가 전부다.**

**15점 눈금**이 306ms(레벨 5 에서 262ms) — 즉 인식 시간 바로 그 자리다.
그래서 매 도형마다 "지금 칠까, 한 칸 내려갈까"가 살아 있다. 이 경계를 인식 시간
언저리에 붙잡아 두는 것이 이 게임에서 가장 섬세한 숫자다.
(2차 튜닝은 이걸 놓쳐서 레벨 5 의 최고 배율 창이 235ms 까지 줄었었다.)

**꼭대기(30점 근처)는 반응으로 닿지 않는다.** 22점 눈금이 153ms 인데 이는 사람의 단순
반응 시간(~200ms)보다도 짧다. 알기 전에 거는 영역이고 기대값은 마이너스다 —
레벨 0 기준 60% 확률로 ~28점, 40% 확률로 목숨 하나(남은 판 전체 ≈ 수백 점)다.
**초보에게는 함정이고, 숙련의 천장이다.** 색 4종을 충분히 익혀 판별이 200ms 아래로
내려가야 열린다.

**망설이는 것도 공짜가 아니다** — 1점 구간은 바닥 바로 위이고, 늦으면 MISS 로 죽는다.
빠르면 WRONG, 느리면 MISS. 그 사이가 스위트 스팟이다.

### 박자는 고정, 빠름의 보상은 점수와 「여유」

도형은 `period` 마다 하나씩, **플레이와 무관하게** 떨어진다(967 → 750ms).
빨리 끊는다고 다음이 빨리 오지 않는다 — 대신 레인이 비고, 그 틈에 다음 기준을 읽는다.
기준이 매 도형마다 바뀌므로 그 여유는 곧 다음 판정의 정확도다.
**빠르면 점수도 오르고 다음도 편해진다.** 느리면 점수도 낮고 다음도 쫓긴다.

그리고 이 고정 박자 덕분에 축이 깨끗하게 갈린다:

| | 무엇이 정하나 |
|---|---|
| **한 판 길이** | 정확도만 — 시간당 도형 수가 일정하므로 틀린 횟수만이 수명을 정한다 |
| **점수** | 배율만 — 즉 얼마나 빨리 끊었나 |

봇으로도 확인된다. react(200/300/400) 세 봇의 생존 시간이 **50.7 / 50.8 / 50.8초로 같고**,
점수만 822 / 548 / 546 으로 갈린다.

## 3. 난이도 — `DIFFS` 표 하나

레벨은 **처리된 도형 수**로 오른다. 튜닝은 이 표만 고친다.

```js
const DIFFS = [
  //                                              낙하    주기    틈
  { upTo:  12, speed: 12.0, period: 58, lure: 0.40, switchEvery: 1 },  // 806ms  967ms  161ms
  { upTo:  30, speed: 12.4, period: 55, lure: 0.46, switchEvery: 1 },  // 780    917    137
  { upTo:  55, speed: 12.8, period: 52, lure: 0.52, switchEvery: 1 },  // 755    867    112
  { upTo:  85, speed: 13.2, period: 50, lure: 0.58, switchEvery: 1 },  // 732    833    101
  { upTo: 125, speed: 13.6, period: 47, lure: 0.64, switchEvery: 1 },  // 711    783     72
  { upTo: Infinity, speed: 14.0, period: 45, lure: 0.68, switchEvery: 1 },  // 690  750   60
];
```

**`period` ≥ 낙하 프레임을 반드시 지킨다.** 깨지면 도형이 둘 겹쳐 위험-보상 축이
뒤집히거나(9장 2차) 생성이 건너뛰어져 박자가 끊긴다. 시작할 때 `checkPeriod()` 가 검사한다.

**`speed` 를 거의 눕힌 것이 이 표의 핵심이다.** 12.0 → 14.0, 겨우 17% 만 오른다.
속도를 올리면 ×3 창이 인식 시간 아래로 내려가 고민이 도박이 되기 때문이다(2장).

**`switchEvery: 1` — 기준은 매 도형마다 바뀐다.** 전환 비용이 0 이라(HUD 가 다음 기준을
상시로 보여주므로 정지도 배너도 필요 없다) 매번 바꿔도 죽은 시간이 늘지 않는다.

그래서 레벨과 함께 오르는 것은 `lure`(0.40 → 0.68)와 **`period`(967 → 750ms)** 다.
주기가 줄면 다음 기준을 미리 읽을 틈이 줄어든다 — 지각이 아니라 **준비**를 압박한다.

### 채점 방식 — `?score=curve|linear|tier`

| | 점수 | 눈금 | 성격 |
|---|---|---|---|
| **`curve` (기본)** | 1~30 연속 | 30/22/15/8 | `30·(1−p)^1.4`. 아래 40% 가 거의 평평 — 쉬어가는 구간이 있다 |
| `linear` | 1~30 연속 | 30/24/18/12 | `30·(1−p)`. 순수 직선. 끝까지 1ms 를 다툰다 |
| `tier` | 10/20/30/40 | — | 옛 칸 단위. 경계에 점수 절벽이 있다 |

최고 기록은 방식마다 따로 저장된다(`judge:best:<방식>`) — 섞이면 비교가 안 된다.

### 느낌을 직접 재보는 법

```
index.html?speed=12.6&lure=0.5&switch=5&period=55&score=curve
```

준 값으로 모든 레벨을 평평하게 만든다. 화면 아래에 `튜닝됨 · …` 이 뜨고,
그 상태의 기록은 기본 난이도와 비교할 수 없다. 손으로 느낌을 빨리 좁히기 위한 것이다.

- **react 세 봇의 생존이 50.7 / 50.8 / 50.8초로 똑같다.** 고정 박자의 결과다 —
  시간당 도형 수가 같으니 오판 횟수만이 수명을 정한다. 점수만 갈린다.

> **이 수치는 밸런스 확인용이고 재미의 증거가 아니다.** 재미는 직접 10판 해보고 판단한다.
> (프로젝트 지침)

### 속도-정확도 교환 — 이 게임이 실제로 묻는 것

위 봇은 오판율이 고정이라 "빨리 볼수록 더 틀린다"를 못 잡는다.
`오판율 = 2% + 33%·exp(−반응/190ms)` 로 두고 12시드씩 120초 상한으로 재면:

| 반응 | 생존 | 도형/초 | 빈 시간 | 최장 공백 | **총점** |
|---|---|---|---|---|---|
| 200ms | 22.9초 | 1.07 | 50% | 0.88초 | 353 |
| 300ms | 30.9초 | 1.08 | 44% | 0.75초 | 328 |
| 400ms | 47.9초 | 1.11 | 38% | 0.70초 | **505** |
| 600ms | 75.7초 | 1.14 | 25% | 0.48초 | 389 |

- **도형/초가 1.07~1.14 로 사실상 같다.** 고정 박자가 의도대로 동작한다.
  실제 생성 간격은 **937ms ± 42ms** 이고, 그 편차는 레벨이 바뀌며 주기가 짧아지는 몫이다
  (한 레벨 안에서는 정확히 일정하다).
- 양 극단이 진다. 무모(200ms) 353점, 과신중(600ms) 389점. 400ms 근처가 고원이다.

### 죽은 시간 — 고정 박자의 값

| | 값 |
|---|---|
| 아무것도 칠 게 없는 시간 | **빨리 칠수록 늘어난다** — 50%(200ms) → 25%(600ms) |
| 조건 전환이 차지하는 몫 | 0% (정지가 없다) |
| 가장 긴 공백 | 0.88초(200ms) → 0.48초(600ms) |

**이것이 고정 박자의 대가다.** 주기가 낙하보다 길어야 하므로, 빨리 끊을수록 레인이 오래 빈다.
기획자가 6차에서 "잠시 틈이 있을 수 있다"고 미리 받아들인 값이다.
다만 그 틈은 기준이 매 도형마다 바뀌는 지금 **다음 기준을 읽는 시간**으로 쓰인다.

줄이고 싶으면 노브는 하나뿐이다: **×1 칸을 좁히는 것**.
주기 ≥ 낙하 시간이고, 낙하 시간은 "×3 경계 = 300ms" + 20/20/20/40 분할이 정한다.
25/25/25/25 로 바꾸면 낙하가 795 → 645ms 로 줄어 주기도 그만큼 짧아진다.
`speed` 나 `period` 를 건드려 줄이려 하면 2장의 시간 표가 무너진다.

## 5. 재현성 (원칙 1)

- 게임 로직의 난수는 `mulberry32(seed)` 하나뿐이다. 연출(파편·흔들림)에만 `Math.random` 을 쓴다.
- 시드가 정하는 것: 도형 색 순열, 기준 색 순열. **결과는 정하지 않는다.**
- **고정 타임스텝**이라 주사율과 무관하게 같은 틱 열을 밟는다. 입력 로그 `[{t: ms}]` 의 `t` 는
  틱 번호와 1:1 대응한다.
- 게임 오버 화면의 `시드 · 재현` 버튼 → `window.__judge.replay(seed, inputs)` 로 다시 돌려
  점수가 같은지 화면·콘솔에 표시하고, 이어서 그 판을 그대로 재생한다.

## 6. 저장 · 리더보드

- 로컬 최고 기록: 어댑터(`window.storage` → `localStorage` → 메모리), 키 `judge:best`,
  값 `{score, seed, inputs}`.
- 온라인 리더보드는 Supabase REST `fetch`. **지금은 꺼져 있다** — 이 저장소에 붙은
  Supabase 프로젝트가 없어 URL/키가 비어 있다. 켜려면:

  ```js
  window.__judgeLB = { url: 'https://xxxx.supabase.co', key: '<anon key>' };
  ```

  테이블 `judge_scores(name text, score int, seed text, created_at timestamptz default now())`,
  RLS 는 select/insert 전체 허용. URL 이 비면 네트워크 호출을 아예 하지 않고,
  켠 뒤 실패해도 게임은 그대로 돈다.
- 1위를 받아오면 HUD 왼쪽에 `세계 1위 23,000` 으로 **플레이 중** 표시한다(원칙 6).

## 8. 하지 않은 것 (원칙 9)

콤보, 연속 보너스, 아이템, 스테이지, 캐릭터, 업그레이드, 모양 조건, 복합 조건, 부정 조건 —
전부 없다. 코어 루프가 재미있다고 확인되기 전에는 붙이지 않는다.

### 다음에 시험해 볼 것 (코드 말고 여기에만 적는다)

1. **연속 채점이 피로한가.** 7차에서 기획자가 미리 짚은 비용이다.
   `curve` 의 아래 40% 평평 구간이 답이 되는지, `?score=linear`(순수 직선)와 비교해 볼 것.
   **지금 가장 중요한 열린 질문.**
2. **꼭대기(30점 근처)가 함정인가 천장인가.** 22점 눈금이 153ms 라 반응으로 닿지 않는다.
   충분히 익히면 열리는 영역이라 좋은 천장일 수도, 초보를 죽이는 함정일 수도 있다.
   `?speed=9` 로 창을 204ms 까지 늘려 비교할 수 있다.
3. **매번 바뀌는 게 정말 나은가 — `?switch=3` 과 비교.** 4차의 「걸리는 점」 참고.
4. **한 판이 짧은가.** 노브는 목숨뿐이다(`LIVES`). 속도·구역은 2장의 시간 표라 건드리면 안 된다.
5. **빈 시간 50%(빨리 치는 쪽)가 견딜 만한가.** 고정 박자의 대가다(4장).
   줄이려면 노브는 **×1 칸을 좁히는 것** 하나뿐이다 — 25/25/25/25 로 바꾸면 주기가 795 → 645ms.
6. **주기 곡선(967 → 750ms)이 맞는가.** `?period=50` 처럼 고정해서 비교할 수 있다.

## 8.5 채점 방식 — 왜 연속으로 바꿨나 (측정)

7차 관찰("×3 하단 / ×2 상단에서 실력 차가 난다")을 검증하려고, 사람 모델에
**반응 떨림(σ = 45ms)** 을 넣고 채점 방식만 바꿔 재봤다.
아래 수치는 판단 근거이고, 결론대로 연속 채점을 기본으로 바꿨다.

### (1) 한 도형 단위 — 연속이 낫다

40ms 차이 나는 두 플레이어(280ms vs 320ms)를 점수가 몇 표준편차만큼 갈라내나:

| 채점 | 점수/도형 (280ms) | (320ms) | **판별력** |
|---|---|---|---|
| `tier` | 25.88 ± 1.46 | 22.37 ± 1.23 | 2.60 |
| `linear` | 18.51 ± 0.58 | 16.76 ± 0.56 | **3.05** |
| `curve` | 18.65 ± 0.86 | 16.03 ± 0.86 | **3.04** |

연속 채점이 **17% 더 잘 가른다.** 이유는 단순하다 —
사람들이 몰리는 지점(×3 하단 ≈ 306ms)이 하필 칸 경계인데,
반응 떨림이 ±45ms 라 **같은 실력이 우연히 30점과 20점으로 갈린다.**
원칙 1(결과는 실력이 결정한다)에 정면으로 걸리는 지점이다.

### (2) 한 판 단위 — 채점 방식은 상관이 없다

"실력"을 **속도-정확도 곡선 자체**로 정의하고(같은 300ms 에 숙련 6.5% / 초보 10.9% 오판)
80판씩 재면:

| 실력 | 생존 | `tier` 총점 | `curve` 총점 | 20판 최고 (`tier`) |
|---|---|---|---|---|
| 숙련 | 46.2초 | 596 ± 359 | 422 ± 249 | 1,477 |
| 보통 | 35.2초 | 459 ± 263 | 327 ± 185 | 1,089 |
| 초보 | 27.8초 | 361 ± 207 | 258 ± 146 | 825 |

숙련 vs 초보 판별력은 **`tier` 0.80, `curve` 0.80 — 똑같다.**
총점이 거의 그대로 생존 시간을 따라간다(596/361 = 1.65, 46.2/27.8 = 1.66).

**즉 순위를 정하는 것은 이미 "얼마나 정확한가"이지 "얼마나 높이 치는가"가 아니다.**
채점 방식은 순위를 바꾸지 않는다. 바꾸는 것은 **매 순간의 피드백이 정직한가**다.

### 결론 — 연속 채점을 기본으로 (7차에 적용)

순위에는 영향이 없고, 한 도형 단위 정직함만 얻는다. 그 효과는 봇에서 바로 보인다:
칸 채점에서 **548 vs 546 으로 사실상 같던** react(300)과 react(400)이
연속에서는 **386 vs 261 로 48% 갈린다.** 100ms 의 실력 차가 비로소 점수에 나타난다.

기획자가 걱정한 두 가지는 이렇게 정리된다:

- **콤보를 못 붙인다** → 애초에 못 붙인다. 원칙 9 와 요청서 10장이 콤보를 금지한다. 잃는 것이 없다.
- **끝까지 집중해야 해서 피로하다** → 진짜 비용이다. `curve` 가 그 답이다.
  `(1−p)^1.6` 은 아래쪽 40% 가 거의 평평해서, 이미 늦었으면 **쉬어가는 구간**이 남는다.
  `linear` 에는 그게 없다(그래서 판별력이 같은데도 `curve` 를 권한다).

띠는 그대로 뒀다 — 색·크기·소리도 띠에서 가져오고, 라벨만 점수 사다리(30/22/15/8)로 바뀐다.
**겨눌 목표(금색 칸)와 또렷한 느낌은 유지하고, 숫자만 정밀해진다.**
게임 오버 화면의 칸 히스토그램은 **「한 방 평균 +14.9 · 최고 +19」** 로 바꿨다 —
연속 채점에서 쫓을 숫자는 이쪽이다.

## 9. 플레이테스트 기록

### 1차 — 규칙 전달 실패

> "아래쪽에 틀린 도형이 있고 위에 맞는 도형이 나올 때 위쪽 도형을 선택하는 방법을 모르겠어."

요청서를 쓴 사람이 자기 게임의 조작을 못 찾았다. 완료 기준 1(설명 없이 3초)과 원칙 3 위반.
게다가 위엣것을 노려 탭하면 아래 틀린 도형이 눌려 목숨이 깎였다 —
규칙을 모르는 사람이 규칙을 배워야 할 순간에 처벌만 받는 최악의 실패 방식.

판정 커서(`▶ ◀`), 대기 도형 축소, 상시 안내, 틀린 순간 교습을 넣어 규칙을 네 겹으로 말하게 했다.
전부 연출 계층이라 봇 수치·재현성은 그대로였다.

### 2차 — 「너무 루즈하고 지루해」 → 코어 루프 교체

> "그럼 결국 1배에서 선택하는 것인데 너무 루즈하고 지루해."

**느낌을 숫자로 바꿔보니 그대로였다.** 사람 모델(반응 300ms)로 90초를 재면:

| | 시간 배분 |
|---|---|
| 칠 수 있음 | **19%** |
| 막혀서 대기 | 54% |
| 빈 화면 / 전환 | 27% |

**시간의 80%가 할 일이 없었다.** 그리고 배율은 이랬다:

- 나는 `speed×gap > 200px` 을 **반응 0ms 인 perfect 봇** 기준으로 맞췄다.
  반응 300ms 인 사람은 60~70px 아래에서 누르므로 같은 상황이 ×1 이 된다.
  **봇 기준은 통과했는데 사람 기준은 실패한 것이다.** 내 튜닝 실수다.
- 더 나쁜 것: ×3 이 나오는 순간은 화면이 비어 있을 때, 즉 **위험이 하나도 없을 때**였다.
  실제 판단은 아래쪽 ×1 에서 일어났다. **위험-보상 축이 뒤집혀 있었다.**

`DIFFS` 만으로 고칠 수 있는지 5개 후보를 재봤다. 못 고친다:

| | ×3 창 | ×3 비율 | 빈 시간 |
|---|---|---|---|
| 현재 3.4/64 | 477ms | 45% | 80% |
| 7.0/44 | 232ms | **0%** | 74% |
| 11.0/36 | 147ms | **0%** | 70% |
| 13.0/33 | 125ms | **0%** | 69% |

속도를 올리면 ×3 창이 반응 시간보다 짧아져 ×3 이 아예 사라지고, 빈 시간은 거의 안 준다.
계산으로도 막힌다 — 막힌 대기 시간 = `gap` 프레임인데, 사람이 ×2 를 잡으려면
`speed×gap > 200 + speed×18` 이 필요하다. **대기를 줄이려면 속도를 올려야 하고,
속도를 올리면 줄이 아예 안 생긴다.** 줄 자체가 문제였다.

**근본 원인:** 배율은 화면 위치로 재는데 플레이어의 시계는 "칠 수 있게 된 순간"부터 간다.
줄이 그 둘을 갈라놔서, 배율이 "내가 얼마나 빨랐나"가 아니라
"화면이 얼마나 비어 있었나"를 재고 있었다.

**고친 것: 화면에 도형을 하나만 두고, 다음 도형을 타이머가 아니라 처리 즉시 내보낸다.**
그러면 y 와 "망설인 시간"이 다시 같은 것이 된다.

| | 이전 | 지금 |
|---|---|---|
| 점수/초 (사람 260ms) | 9.7 | **21.3** |
| 배율이 반응에 반응하는가 | ×2.06 → ×1.91 (거의 무반응) | ×3.00 → ×1.00 |
| 도형/초 | 0.83 | 1.44 |
| safe / perfect | 37.7% | 24.1% |
| 빈 시간의 성격 | 26~31%, 긴 구간 | 28~31%, 대부분 83ms 박자 (최장 = 전환 배너 1초) |
| 생존 편차 (react 300) | 16~120초 | 32~88초 |

### 3차 — ×3 경계에 인식이 걸린다 (좋은 신호) + 전환을 난이도 축으로

> "오 훨씬 괜찮네."
> "나의 감각으로는 ×3의 거의 끝에서 인식하게 돼. 그래서 틀려도 칠지, 안전하게 내려올지
> 고민하게 돼. 흥미로운 포인트이고 게임의 재미를 결정할 부분이라 섬세하게 조절해야 해."
> "조건 전환 시간을 줄이고, 조건을 계속 바꾸는 방식은 어떨까?"

**노린 지점이 그대로 맞았다.** 그리고 이 보고가 2차 튜닝의 남은 버그를 드러냈다 —
레벨이 오르면 ×3 창이 344ms → 235ms 로 줄어, 기획자가 재밌다고 한 그 딜레마가
고레벨에서 **도박으로 바뀌어** 사라지고 있었다.

고친 것:

| | |
|---|---|
| **속도를 눕혔다** | 12.0 → 14.0 (17%). ×3 창을 295~344ms, 인식 시간 언저리에 붙잡아 둔다 |
| **난이도를 전환으로 옮겼다** | `switchEvery` 7 → 3, `lure` 0.40 → 0.62. 지각이 아니라 억제를 압박한다 |
| **전환 공백을 없앴다** | 멈춤 0.9초 → **0.26초**. 배너는 0.76초 동안 남아 다음 도형이 떨어지는 사이에 옅어진다 |
| **배너를 가로 알약으로** | 세로로 쌓은 큰 원이 떨어지는 도형과 헷갈렸다 |
| **튜닝 파라미터 공개** | `?speed=&lure=&switch=&beat=` — 기획자가 왕복 없이 직접 느낌을 좁힌다 |

1.2초 공백은 원래 "도형이 여럿 남은 채 전환하면 판정이 애매해진다"를 막으려던 장치였다.
2차에서 도형을 하나로 줄이면서 그 공백은 **존재 이유가 이미 사라져 있었는데** 남아 있었다.
가장 긴 공백이 1.00초 → **0.41초** 로 줄었다.

### 4차 — 기준을 매번 바꾸고, 팝업 대신 HUD 에 「지금 ▸ 다음」

> "여기서 도형이 항상 바뀌도록 해보자. 바뀌는 안내를 팝업처럼 보여주기보다는
> 제일 윗줄에서 지금 기준 오른쪽에 다음 기준을 보여주면 될 것 같아."

맞는 방향이었고, 그 결과 **전환 정지와 배너를 통째로 없앨 수 있었다.**
팝업은 "전환을 놓치지 않게" 하려던 장치인데, 상시 표시가 그 일을 더 잘 한다.
그리고 전환 비용이 0 이 되자 **매 도형마다 바꾸는 것이 가능해졌다**(`switchEvery: 1`).

`switching` 단계가 시뮬레이션에서 사라졌다. 기준은 이제 큐처럼 밀린다 —
도형이 끝나면 「다음」이 「지금」이 되고 새 「다음」을 뽑는다.
미는 시점은 **판정이 끝난 뒤**다(먼저 밀면 방금 그 도형을 새 기준으로 재게 된다).
화면에 도형이 없는 순간에만 밀리므로 판정이 애매해지는 순간은 여전히 없다.

난이도 곡선도 옮겼다: `switchEvery` 가 상수가 됐으니 이제 `beat`(8 → 3 프레임)가
올라간다. 도형 사이의 틈이 곧 **다음 기준을 미리 읽는 시간**이라,
줄어들수록 "지금 것을 판정하면서 다음 기준도 읽어야" 한다.

#### 걸리는 점 — 이걸로 스킬이 바뀌었을 수 있다

이 게임이 시험한다고 적어둔 스킬은 **억제**다. 억제는 습관이 생겨야 성립한다 —
빨강을 연달아 치다가 파랑을 참는 것이 억제다.
**기준이 매번 바뀌면 습관이 생기지 않는다.** 참을 것이 없고, 남는 것은
"HUD 칩과 떨어지는 도형의 색이 같은가"라는 **비교**와, 다음 기준을 미리 읽는 **전환 준비**다.

둘 다 실제 스킬이고 원칙 3(스킬은 하나)도 깨지 않는다. 오히려 `beat` 압박과 맞물려
"지금 판정 + 다음 준비"라는 주의 분배가 ×3 위험-보상과 직접 연결된다.
하지만 **이건 요청서가 적어둔 스킬과 다른 게임**이다.

`?switch=3` 으로 예전 방식(3개마다 전환)과 나란히 비교할 수 있게 해 뒀다.
어느 쪽이 재미있는지는 손으로만 판정된다.

### 5차 — 배율 4단계 (20/20/20/40), 목숨 3

> "상당히 괜찮아졌어. 생명은 3개로 줄이자. 배율의 영역을 ×4~×1 로 네 단계로 두고,
> 넓이는 위에서부터 20/20/20/40 의 비율로 가자."

3단계에서는 칸이 「고민 / 안전 / 망설임」 셋뿐이었다. 4단계가 되면서 위에 한 칸이 더 생긴다:

| 칸 | 레벨 0 창 | 뜻 | 봇 확인 |
|---|---|---|---|
| ×4 | 153ms | 알기 전에 지른다 | 반응 0ms 봇만 잡는다 |
| ×3 | ~306ms | **아는 순간 바로 친다** | 200ms 봇 |
| ×2 | ~458ms | 알고 나서 친다 | 300·400ms 봇 |
| ×1 | ~761ms | 망설였다 | safe 봇 |

3차에서 기획자가 말한 "×3 거의 끝에서 인식한다"는 감각이 이제 **×3/×2 경계(306ms)**
에 정확히 놓인다. 그 위에 닿지 않는 칸(×4)이 하나 더 있는 구조다.

점수/초 격차가 4배 → **5배**(29.0 → 5.7)로 벌어졌다. safe/perfect 는 25.2% → **19.7%**.

목숨은 요청서 값인 3개로 돌아갔다. 한 판이 64초 → 38.5초가 되어
요청서 완료 기준 4(45~75초)는 미달이지만, 지침 원칙 5("30초~2분")는 만족한다.
지침이 우선이므로 그대로 둔다.

#### 걸리는 점 — ×4 의 기대값은 마이너스다

레벨 0 에서 ×4 를 노려 지르면 60% 확률로 40점, 40% 확률로 목숨 하나다.
목숨 하나는 남은 판 전체(수백 점)에 해당하므로 **대놓고 손해 보는 선택**이다.
색 4종을 충분히 익혀 판별 시간이 200ms 아래로 내려간 뒤에야 이득이 된다.

의도대로면 좋은 천장이고("드디어 ×4 를 잡았다"), 아니면 초보를 죽이는 함정이다.
`?speed=9`(×4 창 204ms)와 나란히 해보면 갈린다.

### 6차 — 생성을 고정 박자로 (기획자 지시)

> "사용자의 플레이와 무관하게 도형이 일정한 간격으로 떨어졌으면 좋겠어. 잠시 틈이 있을 수 있어.
> 떨어지는 것은 고정된 감각으로 인지하되, 동일한지 여부를 판단하는 거야."

2차에서 세운 불변식 **"다음 도형은 타이머가 아니라 지금 것이 처리되는 순간 나온다"** 를
뒤집는 변경이다. `CLAUDE.md` 가 이런 변경은 근거를 여기 먼저 적으라고 요구하므로 적는다.

**근거:** 판단해야 할 것이 "같은 색인가" 하나라면, 리듬은 변수가 아니라 배경이어야 한다.
박자가 플레이에 따라 흔들리면 플레이어는 색 판단 외에 템포까지 추적해야 한다.

**제약:** `period` ≥ 낙하 시간. 주기가 낙하보다 짧으면 도형이 둘 겹치고,
그 순간 배율이 "내 반응"이 아니라 "화면이 얼마나 비었나"를 재게 된다 — 2차의 실패 그대로다.
낙하 시간은 "×3 경계 = 300ms" + 20/20/20/40 분할이 정하므로 주기는 약 0.95초에서 출발한다.
코드가 시작할 때 `checkPeriod()` 로 이 부등식을 검사한다.

**뜻밖의 이득 — 축이 직교했다.**

| | 무엇이 정하나 |
|---|---|
| 한 판 길이 | **정확도만** (시간당 도형 수가 일정하므로) |
| 점수 | **배율만** (얼마나 빨리 끊었나) |

react(200/300/400) 세 봇의 생존이 **50.7 / 50.8 / 50.8초로 똑같고** 점수만 822/548/546 으로
갈린다. 그리고 주기가 늘어난 덕에 5차에서 미달이던 완료 기준 4(react(300) 45~75초)가
38.5초 → **50.8초**로 돌아왔다. **완료 기준 1~4 전부 통과.**

**대가:** 빨리 칠수록 레인이 오래 빈다(빈 시간 50% @ 200ms, 최장 공백 0.88초).
기획자가 "잠시 틈이 있을 수 있다"고 미리 받아들인 값이다.
그 틈은 기준이 매번 바뀌는 지금 다음 기준을 읽는 시간으로 쓰인다.
바닥선 아래에 얇은 막대를 두어 다음 박자까지를 눈에 보이게 했다 —
"고정된 감각으로 인지"를 돕기 위한 것이고, 판정 구역이 아니라 바닥 아래에 둔 것은
"언제까지 쳐야 하나"로 오독되지 않게 하기 위해서다.

### 7차 — 배율 칸을 버리고 1~30점 연속으로

> "많은 플레이어들이 3배 하단 / 2배 상단 정도에서 성공하게 돼. 결국 그 부분에서 실력의
> 차이가 나게 돼. (…) 1배~4배 같은 방식보다 차라리 각 구간을 연속적으로 (1점~30점처럼)
> 구성해서 각 점수를 합해나가는 건 어떨까? 물론 이 방법은 콤보를 적용하기 힘들고,
> 끝까지 집중해야만 해서 피로도가 높아지긴 해."

**관찰이 정확했고, 측정이 뒷받침했다.** 사람들이 몰리는 지점이 하필 칸 경계라
반응 떨림(±45ms)이 같은 실력을 30점과 20점으로 가르고 있었다 — 원칙 1 위반이다.
연속으로 바꾸니 한 도형 단위 판별력이 17% 오르고(8.5장), 봇에서도
react(300) vs react(400)이 **548 vs 546 → 386 vs 261** 로 갈렸다.

기획자가 스스로 짚은 두 비용 중 하나는 사라지고 하나는 남았다:

- **콤보** — 애초에 붙일 수 없다. 원칙 9 와 요청서 10장이 금지한다. 잃는 것이 없다.
- **피로도** — 진짜 비용이다. 그래서 순수 직선이 아니라 지수 1.4 로 살짝 휘었다.
  아래 40% 가 거의 평평해서 "이미 늦었으면 쉬어가는" 구간이 남는다.
  덤으로 직선이면 safe/perfect 가 40% 라 완료 기준 4에 걸리는데, 곡선은 26.9% 다.

띠·색·소리·화면 튐은 전부 유지했다. 바뀐 것은 숫자의 정밀함과,
게임 오버의 「한 방 평균 / 최고」뿐이다.

## 10. 실험 기록에 남길 한 줄 (초안)

플레이테스트 10판 뒤에 [`docs/프로젝트-지침.md`](docs/프로젝트-지침.md) 실험 기록 표에 채운다.

| 게임 | 스킬 | 결과 | 교훈 |
|------|------|------|------|
| 3rd-game (골라!) | 억제 → 비교·전환 | *(10판 후 기록)* | **위험-보상 축은 플레이어의 시계로 재야 한다.** 처음엔 배율을 화면 위치로 쟀는데, 도형이 줄을 서면서 위치가 "내 반응"이 아니라 "화면이 얼마나 비었나"를 재게 됐고 축이 뒤집혔다(위험 없는 곳에서 ×3, 판단하는 곳에서 ×1). 화면에 하나만 두고 처리 즉시 다음을 내보내니 위치 = 망설인 시간이 되어 축이 살아났다. **판정 창은 사람의 인식 시간(약 300ms)에 붙잡아 둘 것** — 길면 공짜, 짧으면 도박이고, 난이도는 지각이 아니라 억제(조건 전환 빈도)에서 올려야 딜레마가 유지된다. **봇으로 튜닝할 때 반응 0ms 봇을 기준으로 삼으면 안 된다** — 사람 기준으로는 정반대 결과가 나온다. 그리고 **생성을 고정 박자로 두면 축이 직교한다** — 정확도가 판 길이를, 속도가 점수를 정한다 |
